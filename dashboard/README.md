# Cadence dashboard

The owner's dashboard: TanStack Start (React, SSR on Node), Tailwind v4 and shadcn/ui (Base UI), TanStack Query over a
client generated from the server's OpenAPI document. It is served on the same origin as the API (the server's
`__Host-` session cookie, SameSite=Strict, and its CSRF rule need that); Traefik sends `/api/`, `/v2/` and `/healthz`
to the server and every other path here (`deploy/server/README.md`, Dashboard).

`make dashboard-check` runs in a copy of this directory inside the node image: the image's node against `.nvmrc` and
`engines` (all three name one version), a frozen install, lint, typecheck, unit tests, the build (the route tree it
regenerates must equal the committed one) and the client regenerated beside the committed `src/api/gen`. Neither make
target needs node on the host.

Tests drive the page with `setupUser()` (`src/test/typing.ts`: user-event without its pause after every key and pointer
step, which turned a form re-rendered per keystroke into seconds) and enter a value a test is not about typing in one
input event (`enter`, `replace`: a paste). `src/test/setup.ts` gives `findBy`/`waitFor` 3 s and `vitest.config.ts` a
test 15 s: headroom for `make ci`'s load beside the Go and C++ builds, never a fix for a slow test.

The unit tests fail on any `console.error` a test logs (`src/test/setup.ts`, `src/test/console-guard.ts`): React says
there what is wrong (a duplicate key, an update outside `act`, invalid DOM nesting), and Vitest hides a passing test's
output. A test that expects one mocks it itself (`vi.spyOn(console, 'error').mockImplementation(...)`). The enroll
hint's test reads `deploy/pickle/README.md` and `deploy/midi/README.md`, which the gate copies beside the package.

`design-preview/index.html` is written by `pnpm preview:build` from the real components and tokens; no gate compares it
with them, so regenerate and commit it after a change to the design.

## The theme script and a CSP

The document head carries an inline script (`THEME_SCRIPT` in `src/lib/theme.ts`) that applies the stored theme
before the first paint; TanStack Start's hydration scripts are inline too. No Content-Security-Policy is sent today.
When one lands, `script-src` must allow them with a per-response nonce (or the theme script's sha256), set on the theme
script's entry in `head().scripts` in `src/routes/__root.tsx`; never `'unsafe-inline'`.

## Local work against the dev stack

The server accepts a cookie request only from the origin `CADENCE_PUBLIC_ORIGIN` names, and the dev stack sets it from
`CADENCE_DEV_ORIGIN`. Point it at this dev server:

1. From the repo root: `CADENCE_DEV_ORIGIN=http://localhost:3000 make dev-up`
2. Set the owner password from a file outside the repo, on stdin (never an argument):
   `docker compose -f deploy/dev/compose.yml exec -T server /cadence-server admin password set < <file>`
3. Here: `pnpm dev`, then open http://localhost:3000 (use that exact host: `127.0.0.1:3000` is another origin)

Vite proxies `/api` (the live feed's websocket too) to `http://127.0.0.1:${CADENCE_DEV_PORT:-8080}` with
`changeOrigin: false`, so the browser's `Origin` and `Host` reach the server unchanged. The dev stack runs on plain
http (`CADENCE_COOKIE_INSECURE=1`), so its cookies are `cadence_session` and `cadence_browser`.

The dev stack also runs this dashboard as its image (`dashboard`) behind its edge (`edge`, Traefik with
`deploy/dev/edge.yml`), the one origin at `${CADENCE_DEV_PORT:-8080}`: `/api/`, `/v2/` and `/healthz` go to the
server, every other path to the dashboard, as Traefik splits the host in `deploy/server/compose.yml`. With the default
`CADENCE_DEV_ORIGIN` (`http://127.0.0.1:8080`), `make dev-up` alone serves the built dashboard there; `pnpm dev`
above still reaches the API through the same edge.

## The SSR server (serve/)

The image runs `node serve/main.ts` (Node runs the TypeScript as is) beside the build in `dist/`, on port 3000:

- `GET /healthz` answers `{"status":"ok"}` for the image's `HEALTHCHECK` (`serve/healthcheck.ts`), unlogged. Behind the
  edge or Traefik the public `/healthz` is the server's.
- The client build's files by their exact path, read once at start (no request path reaches the file system):
  `assets/` (hashed names) cached a year `immutable`, the rest an hour.
- Every other GET or HEAD is Start's (`dist/server/server.js`), rendered with the request's path, query and headers (the
  cookie the SSR client forwards) and stopped when the reader goes away. Other methods are 405.
- Every answer carries `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff` and `Referrer-Policy: same-origin`.
- The log (stdout, JSON lines): `request` with `method`, `path` (no query or fragment, at most 256 characters),
  `status` and `ms`; `dashboard_listening`, `dashboard_stopping`; `render_failed` and `dashboard_crashed` with an
  error's class only. `console` is replaced at start: a library's call becomes `{"msg":"console","method":…}` with an
  error's class, never its arguments (M7b-D6, rule 8). Node's own warnings name their class only.
- The SSR client gives up on an API call after `SSR_TIMEOUT_MS` (10 s, `api/server.ts`), so a hung API never holds a
  page's render; such a page says "The server did not answer in time."
- `CADENCE_API_INTERNAL` missing stops the server at start (`config_missing`, the variable named, never a value).

## End to end (Playwright)

`e2e/` holds the Playwright specs `make e2e` runs (its dashboard block, after the other blocks enrolled the sim and set
the owner password): login (a submit with scripts off, which posts and never puts the password in the URL, a wrong
password, then the owner's), the devices list with the sim online, its page, a capability config through the editor
applied on the sim, a secret that reaches the sim (its capability's next generation applied) and then shows as set,
never as its value, a token shown once, a refusal in a dialog that keeps the focus (Chromium drops the focus of a
disabled button, which jsdom cannot show), a turn the sim's say file starts on the live timeline, the sign-out, and a
session ended elsewhere that the feed (1008) brings back to the login. Then the newer pages (M7c):

- `providers.spec.ts`: a `fake-stt` instance from the module catalog (its kind's group, its schema's config form),
  Test answering OK with its ms, deleted; the focus back on Add a provider each time.
- `modes.spec.ts`: a mode added, named in the global `allowedModes` through the modes page's link (the defaults put in
  first when the key was unset), its delete refused inline (409 `in_use`), the key put back (Reset, or the item
  removed), then deleted.
- `device-pages.spec.ts`: the sim renamed in its header, found under the new name in the list, and named back (through
  the API from the page when the spec failed between the renames, so no later spec or the Home Assistant client's
  smoke finds it renamed); a turn
  the say file starts listed first in Conversations (Button, the transcript, No reply, `device_volume`), its drawer
  with the call's arguments and its result, the focus back on Open, and the transcript in neither the URL nor the
  storage; Health's CPU figure and the top processes by name (process, PID, CPU, memory: no
  command line).
- `logs.spec.ts`: Live on, a fresh line of the sim's log probe on the live tail with its `sim-probe` source, kept in
  neither the URL nor the storage, then Live off and the stored lines back.

The e2e's dashboard block runs those turns on a scripted model (`llm-dash`: `device_volume` to 10, then nothing said),
so the conversations show a tool.

- They run in compose's `playwright` service (`deploy/dev/playwright.Dockerfile`: the pinned official Playwright image,
  its version equal to `@playwright/test` in the lockfile, with this package's frozen install), in the edge's network
  namespace, so the browser's origin is `CADENCE_DEV_ORIGIN` as on the host. One worker, Chromium, no retries.
- `deploy/dev/playwright.sh` runs them: the owner's password goes on the container's stdin (never a mount, an argument or
  a log); a spec asks for a turn on its output (`cadence-e2e:want-turn`), which the script answers with the sim's say
  file, and for a line of the sim's log probe (`cadence-e2e:want-logprobe <text>`: letters, digits, spaces, `_` and
  `-`), which it writes into the sim's probe file (mode 600, the sim's user), and names what it saw that no log may
  carry (`cadence-e2e:learned …`: its sessions' cookies, the token, the secret it typed, the value the scripts-off
  login posted; `cadence-e2e:signed-in` after each sign-in), which the script hands to the e2e's privacy greps and
  leaves out of the output it prints. It fails (exit 4) when no sign-in was reported or fewer cookies were learned
  (`cadence-e2e:learned-cookie …`, apart from the other values) than two a sign-in, as a marker it could no longer read would leave them out of the greps. The container's log
  driver is `none`, so no daemon log keeps that output.
- No trace (one records the login's body and every typed value) and no video. A failure leaves a full-page screenshot
  with every field and the one-time token box masked, and Playwright's `error-context.md` without its page snapshot
  (`PLAYWRIGHT_NO_COPY_PROMPT`, read in Playwright's own source and undocumented: check it again at each Playwright
  upgrade), in `build/dashboard-e2e/` (git-ignored). `playwright.sh` greps every one's bytes for the run's secrets
  (the password, what the specs learned, and `DIR/secrets` when the caller gives one, as the e2e does) and on any hit
  removes the whole directory and fails (exit 3). A screenshot's pixels are guarded by its masks alone. A matcher on an
  element that shows a secret would write it into its error: the specs check such values with `pageHolds` (a boolean),
  the URL and the storage with `keptPastPage` (a boolean), and wait for the token's dialog to close without a locator.
  The fake transcript (`TRANSCRIPT` in `e2e/sim.ts`, fixed test text, never a user's) is not one of the run's secrets:
  learning it would turn every timeline or conversations failure into exit 3 with its screenshots gone. Instead, an
  element that shows it (the timeline, a conversations row) is checked with `holdsText` (a boolean polled by
  `expect.poll`), so no matcher writes it into an error or `error-context.md`; a failure screenshot's pixels may still
  show it. The probe line of `logs.spec.ts` is no secret either: the e2e greps every log for its prefix.
- Locally, against a stack you brought up and enrolled (the e2e's first blocks), with the password in a mode-600 file
  of a mode-700 directory: `CADENCE_DEV_PORT=<port> CADENCE_DEV_ORIGIN=http://127.0.0.1:<port> sh
  deploy/dev/playwright.sh <project> <dir> [playwright args, e.g. tokens.spec.ts]`. Rule 7: the specs change
  `system.metrics`' interval, the sim's Soloist key, its name (named back) and, through the turns' scripted
  `device_volume`, its level down to 10; never an alarm or a pairing, and never a volume up.

## The API client

`src/api/gen` is generated by `@hey-api/openapi-ts` (fetch client, SDK, TanStack Query options) without a shared client
instance: every SDK call and query option takes `client`, so nothing can skip the wrapper.

- `createApiClient({ onUnauthorized })` in the browser: base `/api/v1` (relative, same origin), `credentials:
  'same-origin'`, `X-Cadence-CSRF: 1` on every method but GET and HEAD, redirects refused, `cache: 'no-store'` (no answer, with its
  transcripts, memories, task text or media metadata, lands in the browser's disk cache: rule 8), an error answer turned into
  an `ApiError` (`status`, `error`, optional `path` and `detail` from the server's `ErrorBody`; a body that is no
  `ErrorBody` is `unexpected_response`), and `onUnauthorized` called on a 401. A failed fetch (offline, aborted)
  stays the error fetch threw.
- `createServerApiClient({ cookie })` on the ssr server, one per request: base `${CADENCE_API_INTERNAL}/api/v1`
  (`CADENCE_API_INTERNAL` is an origin on the internal network, such as `http://cadence-server:8080`), the incoming
  `Cookie` header forwarded, the same CSRF header and error mapping. A missing or malformed variable throws, naming the
  variable and never its value.

- The session operations (`/session`: login, logout, the session check) never call `onUnauthorized`: a wrong password
  and a session already gone are their callers' to word. A 429's `Retry-After` (whole seconds) is `ApiError.retryAfter`.
- The router's context holds `api`: `requestApiClient` makes the ssr client per request (the incoming `Cookie`) and the
  browser's once per tab, with `onUnauthorized` returning to the login. Components read it with `useApi()`.
- The generated query keys carry the client's `baseUrl` (absolute on the ssr server, relative in the browser). Wrap
  every generated query option in `sharedKey(...)`, which drops it, so the ssr server's prefetched queries hydrate under
  the keys the browser asks for and the internal origin stays out of the page (`shared-key.test.ts` asserts both).
- The query client (`api/query-client.ts`) retries only a failed fetch or a 5xx, and keeps answers fresh for 30 s, so
  a hydrating page does not fetch what the ssr server just did. Failed queries are not dehydrated into the page. The
  session query never retries, so a down API shows the layout's error page (codes, Try again) at once.
- `describeError` words an error in codes from an `ApiError`, from its fields, or from its message (`api <status>
  <code>[ <detail>]`), so an error the ssr server serialized into the page without its class renders the same text. A
  failed fetch is known by its message, with its class or without (undici's `fetch failed` and the browsers' own); any
  other `TypeError` is a bug in the page and says so.

## Session and login

- Every route but `/login` sits under the pathless `_authed` layout, whose `beforeLoad` (`requireSession`) needs `GET
  /api/v1/session` to answer `authenticated: true` (the cached answer, the ssr server's when it rendered the page);
  otherwise it redirects to `/login?redirect=<the page>`. The layout opens the live feed and the shell.
- `/login` posts the password with `createSession` directly (a mutation would keep it in the cache) from an
  uncontrolled field; 204 clears the cache and goes to `redirect` if it is a path on this origin (`safeRedirect`: no
  absolute url, `//`, `\` or control character, nor dot segments that normalize to `//host`, never `/login`), else `/`. 401 says "Wrong password.", 429 "Too many
  attempts, try again in N s." from `Retry-After`. A reader already signed in is sent on.
- Every form is `method="post"` (a guard test reads each `<form`), the login's with `action="/login"`, and every handler
  calls `preventDefault` first. A submit before hydration (Enter on a slow load) or with scripts off is the browser's
  own: as a GET it would put the password, a secret or a reply in the URL (history, any proxy's access log); as a POST
  the image's server answers 405 without reading the body, and logs only the path. Playwright submits the login with
  scripts off and checks the URL.
- A 401 on any other request, or a feed the server closed 1008 for an ended session, calls `returnToLogin`: one
  navigation to the login with the way back, then `queryClient.clear()`. Sign-out (the header's account menu) is
  `DELETE /session` (a 401 counts as signed out), the login, then the cache cleared; another failure leaves the reader
  signed in with a toast naming the code.
- Every page answers `Cache-Control: private, no-store`.

## The live feed

`src/lib/live/`: one websocket per tab to `/api/v1/live` on the page's own origin, opened by the signed-in layout.

- Pages declare their topics with `useLiveTopics([...])`; the feed sends `{"subscribe": [...]}` with the union of every
  mounted page's topics as each changes (so `logs` only while a page asks for it), at most one frame per 200 ms, far
  under the server's 4 KiB and 10 frames a second. The union is looked at once the tick is over, so a page swap
  (release and want in one commit) sends nothing when the topics stay the same.
- Reconnects back off from 1 s doubling to 30 s, each wait ±25 % (held within 1–30 s), starting over only after a
  connection that stayed open 10 s. A 1008 close, or an upgrade that never opened (a refused upgrade reaches the page
  as 1006), checks the session first: ended means the login, without reconnecting. After a reconnect or a `dropped`
  frame, every query the subscribed topics feed is invalidated, and so is every query a topic feeds when it joins a
  subscription already sent (a page that brings it back missed its events meanwhile, and its cache may still be fresh).
  A reconnect or a `dropped` frame while `logs` is subscribed also leaves a mark in the log stream where lines may be
  missing. Refusal frames (`topic_unknown`, `forbidden`, `invalid`) reach only the console, and only in development.
- Invalidations are coalesced: the keys of every event in a 250 ms window are invalidated once each, with
  `cancelRefetch: false`, so a burst (a turn's steps, a task's progress) neither refetches per event nor cancels a
  refetch on its way. A key whose query is still fetching when its window ends waits for the next one: that fetch may
  have read the server before the change.
- The header's tally shows Connecting, Live, Reconnecting or Disconnected.
- Streams, in memory only and gone with the layout at sign-out: `useLiveTimeline()` (turns, the agent's visible steps,
  tasks, media sessions; at most 500 events) and `useLiveLogs()` (`log_line`, the feed's `log_line_dropped` counts and
  the gap marks, at most 2000). Transcripts, replies and
  tool data from the feed are shown in the page only, never stored and never logged. A `media_state` that says what the
  device's last one said (a seek, a volume step: same state, session, source and track) is not kept; the overview leaves
  media sessions to the device pages, which follow the `media` topic.
- Span events (`span_start`, `span_update`, `span_end`, `span_dropped`) are kept nowhere: they go, with every gap of
  the feed while `traces` is subscribed (a `joined` one too), to the pages that listen (`useSpanSignals`), which fold
  them into their own traces.
- Event type → queries invalidated (`invalidation.ts`; `device` narrows to the event's device):

  | Event | Queries |
  | --- | --- |
  | `memory_changed` | `listMemories` |
  | `compaction` | `listDeviceCompactions` (device) |
  | `learning_run`, `learning_op` | `listDeviceLearning` (device), `listMemories` |
  | `mcp_connected`, `mcp_unavailable`, `mcp_tools_changed` | `listMcpServers`, `listMcpTools` |
  | `task_event` | `listTasks`, `getTask`, `inspectTask`; a shown transcript (`inspectTaskTranscript`, its own key) only once the task is done, failed or cancelled |
  | `media_state` | `getDeviceMedia` (device) |
  | `turn_end` | `listDeviceTurns` (device): the server stores a turn before it publishes its end |
  | `device_online`, `device_offline`, `device_added`, `device_renamed` | `listDevices`, `getDevice` (device) |
  | `device_volume` | `getDevice` (device): a media sender's slider can send several a second, one read per window |
  | `device_deleted` | `listDevices`; the device's own queries are dropped, never read again (below) |
  | `group_changed` | `listGroups`, `getGroup`, `listDevices`, `getDevice`: a group created, changed or deleted, or a new leader elected; the devices name their group |
  | `group_state` | `getGroup`: a member's reported sync (state, clock error, queue, rejoins), shown on the group's page |
  | `device_vitals` (`vitals`) | none: it comes every round, and Health reads its metrics on its own interval (a 24 h read is about 1 MB a chart) |
  | `turn_start`, `transcript`, the agent's steps, `log_line`, `log_line_dropped` | none: streams only |

  The overview and the devices list read the list (each device's online flag with it) on those events, on focus and
  after a gap in the `devices` topic, never on a beat; a gap (a reconnect, a `dropped` frame: maybe the server
  restarted, which drops every link, and no device event is replayed) invalidates `listDevices` and `getDevice`
  (`GAP_INVALIDATIONS`). No page subscribes to `vitals`. A `device_deleted` first drops what is still pending for that
  device (`Invalidator.forget`), so no window reads it after its delete. A page that shows the device takes it over
  (`useDeviceDeleted`: it leaves, as after its own delete, below); otherwise the queries that read the device and that
  nothing observes are dropped and the list goes on without it (`forgetDeletedElsewhere`), while one another page still
  observes (a filter on the device) keeps its last answer, as dropping it would have that page read it again.

## Times

Times are worded in the household's zone: the global `timeZone` setting (`UTC`, the server's default, while unset),
read once by `useTimeZone()`, prefetched by the signed-in layout. Until it loads it is `null`, and `Timeline`,
`LogView` and `clockText` show `--:--:--` on the ssr server and in the browser alike.

## Dependencies

Every dependency is pinned to an exact version and the lockfile installs frozen. `pnpm-workspace.yaml` sets
`minimumReleaseAge` to three days (npm's unpublish window), so a hijacked release has time to be pulled before it can
land in the lockfile; pnpm runs no dependency's install scripts unless `allowBuilds` names it (none does). Nothing loads
from a CDN at runtime: the Geist and Geist Mono fonts come from `@fontsource-variable/*` in the bundle (the Latin and

## Forms from JSON Schemas (M7b-D5)

Decision: our own small renderer, written with the device pages (Task 4), not `@rjsf`.

Checked on 2026-11-12 (Context7 and the npm registry): `@rjsf/shadcn` exists and is maintained (6.11.1, released with
`@rjsf/core` 6.11.1 on 2026-11-05), takes React 18 or newer and documents Tailwind v4 (an `@source` on its package).
It does not fit:

1. Our schemas are JSON Schema draft 2020-12. rjsf's Ajv validator defaults to draft-07, and its docs say draft
   2020-12 (`Ajv2020`) "has breaking changes and hasn't been fully tested with @rjsf".
2. It ships its own copies of the shadcn components (Radix, inside the package, with its own `cn`), not ours (Base UI,
   vendored in `src/components/ui`): the design system would reach its forms only through the CSS variables, and a
   second set of primitives would ship.
3. What our forms need beyond a renderer is ours either way: write-only secrets (`{set: true}` shows "set" with a
   replace action, never a value), desired vs applied badges, and a raw-JSON fallback for what the renderer cannot
   show, where rjsf would leave keywords it does not render (such as `not`, which the alarms commands use) to its
   validator.

The renderer covers the subset our schemas use: objects (nested too), strings with `pattern`, `enum`, `minLength` and
`maxLength`, integers and numbers with their bounds, booleans and arrays of scalars. A schema or a part of one outside
that subset (`oneOf`, `anyOf`, `not`, arrays of objects, `$ref` and the like) is edited as raw JSON instead, never
rendered with fields dropped; the server's 422 `path` pointer stays the authority on validity.

As built (`src/components/forms/`):

- `buildForm(schema, value)` (`json-schema.ts`) reads each node for the subset: `object` (`properties`, `required`,
  `additionalProperties` false or true), `string` (`minLength`, `maxLength`, `pattern` compiled with the `u` flag,
  `format` as a note only), an `enum` of strings (a select; with or without `type: string`), `integer` and `number`
  (`minimum`, `maximum`, `exclusiveMinimum`, `exclusiveMaximum`), `boolean` (a switch), and `array` of one of those
  scalars (`minItems`, `maxItems`, `uniqueItems`; options as checkboxes, free items as chips). Annotations (`title`,
  `description`, `default`, `examples`, `$comment`, …) are allowed; any other keyword, a type union, a `const`, a
  pattern the browser cannot compile, or no `type` makes that node raw JSON. So does a value that the node could not
  show whole: one of another type, a key the object does not name, an option the enum lacks.
- The schema is read once, from the value the form opens with. Client validation (`validate.ts`) mirrors the subset:
  required, lengths in characters, pattern, bounds, whole numbers, list length, items once each and each item. Numbers
  are typed as text and read with JSON's own grammar, so a half-typed one is held back with its reason, as is a list
  item typed but not added. An emptied field is no value (its key is left out); an optional switch whose key is left
  out shows the schema's default (else off) and says "Not set: the device decides", and a set one can be cleared; a
  required one left out is off, and the form sends it as `false`. An option list shows its description and marks each
  checkbox when it is wrong.
- `JsonForm` without a schema is the raw JSON editor for the whole document (pretty-printed, it must parse and be an
  object). A refusal with a `path` is put on the field it names (`fieldFor`: the deepest field the pointer leads into,
  a list's item or a raw part's inside included), else shown beside the form with the path; any other error in codes.
  An object's own error (left out though required; the server's 422 about a missing or an extra key in it, whose path
  names the object) shows on its fieldset, described by it. After a failed submit the first wrong field takes the
  focus (a fieldset's or an option list's first control); a form that opens in place (`autoFocus`) focuses its first
  control, and its submit is the quieter `secondary` button (the page keeps its one yellow action).
- `SchemaFields` (`schema-fields.tsx`) is the renderer without a form of its own, which `JsonForm` wraps with its submit: a
  hand-made form (the provider dialog's config) mounts it, asks it at submit for the value (`submit()`, undefined while
  a field holds it back, its errors then shown), and hands it the server's refusal (`refuse(pointer, message)`, false
  when no field has that path).
- The capability pages wire it through `capabilitySchemas` (`components/devices/detail/capability-schemas.ts`): a
  config is edited through the `configSchema` the device declared and a command's arguments through its `argsSchema`,
  each the raw JSON editor where the device declared none (`null`), and where the form cannot show the schema (a root
  `not` or `oneOf`, as `set_alarm` and `cancel_alarm` carry) the raw one with its note. The device settings editor
  renders through it too, from the schemas in `components/settings/settings-catalog.ts` (the server's types and
  bounds).

## Devices

- **List** (`/devices`): name, status, board (the board's name from `GET /boards`), last seen in the household's zone,
  sortable; Enroll a speaker as the page's action and in the empty state. An enrolled device is Online or Offline as
  `GET /devices` says (`online`: linked to the server now), so neither the list nor the overview's counts read a
  detail. It follows the `devices` topic's events (no beat).
- **Enroll wizard** (`/devices/enroll`): the board and a name (trimmed, 1–64 characters, as the server holds it) make the device and its one-time code (`createDevice`
  called directly, so the code reaches no query or mutation cache; it lives in the page's state and nowhere else, never
  logged or stored; the devices list is marked stale after any answer). The page shows the code with its countdown and the one command that enrolls with it: the sim's
  `cadenced enroll … --board sim` (as `deploy/dev/e2e.sh` runs it inside its image), an installer board's
  `build/cadence-install.exe $speaker --tarball "$tarball" --server <this origin> --code <code>` as its readme runs it
  (midi's with `--ota-blocked`), with a line naming that readme for `$speaker` and `$tarball`
  (`enroll/enroll-command.ts`, whose test holds each line equal to `deploy/pickle/README.md`'s and
  `deploy/midi/README.md`'s). The step's title takes the focus once the code is made. It then reads the device
  every 2 s until it is enrolled and online, hides the spent code, and links to its page; a read the server refuses is
  shown in codes and not repeated. An expired code offers a new one, back on the form with the name focused; the reads
  go on until one made 2 s or more after the expiry (the speaker may have used the code after the last read, and the
  server's clock may run behind the page's), decided on the reads alone, so a render after the expiry never ends them
  early. A speaker that enrolled then is followed; otherwise the step says "The code expired before <name> enrolled."
  and its spinner goes. Its pending device stays in the list, its name taken (the server refuses a second device of the same name
  in any case), so the expired code also offers Remove <name>: the device is read once more first (the speaker may
  have used the code after the last read, and one that enrolled stays and is followed), then deleted while still
  pending (`delete-device?status=pending`: a speaker that enrolls between the read and the delete gets 409
  `not_pending`, nothing is deleted, and the device is read again and followed; a 404 counts as removed), the list
  marked stale, and the form opens on the name, saying it is free again. A refusal is worded beside the button, which
  keeps the focus.
- **A device's page** (`/devices/$id`, keyed by the id, so nothing open on one device carries over to the next): the
  name and its status, then its board, last seen and id; each capability as a card (an `h3` over its `h4` parts: its
  state, its desired config with the applied, pending (`gen 4 → 5`) or failed (struck, with the device's code) badge,
  the secrets it declares (in its order, with their descriptions) write-only: "Set" or "Not set", Set/Replace through an
  uncontrolled field cleared as soon as it is read, and Delete after a confirmation; its commands with their arguments and the device's result). The secret field is no
  password field: `type="text"` masked with `-webkit-text-security` (Chromium, Safari, Firefox 114 on),
  `autocomplete="off"`, the name `value`, and the ignore marks of 1Password, LastPass, Bitwarden and Dashlane, so no
  password manager fills it with the dashboard's own saved password or offers to save it. Editors and the secret field
  take the focus when they open and give it back to their Edit, Override or Set button when they close (a reset or a
  delete too, whose own button goes); a config draft survives a new generation arriving while it is edited. The detail
  is read every 2 s while a change is pending on an online device, else every 30 s (a capability's state reaches no
  event but its volume), again after each change, and on its device's `device_online`, `device_offline`,
  `device_renamed` and `device_volume`. The settings table shows each key the
  device may set with the value in force and where it comes from (Overridden, Inherited from the global settings, or
  the Server default), Override or Edit through its schema, and Reset (`null`) back to the inherited value; the server
  validates (`settings_invalid`). The side column holds the media card (the session from `GET /devices/{id}/media`,
  refreshed by `media_state`; no artwork yet: the server serves it, `get-device-artwork?h=`, and showing it is follow-up
  work) and the Say box (`announce-to-device`, 202). The page follows `devices` (its own presence, rename, volume and
  delete), and its activity timeline `sessions`, `agent` and `media` for this device only.
- **Rename** (the header's Rename): the name in place of the title, trimmed and checked as the server does (1–64
  characters, no control or format character; `components/devices/device-name.ts`, shared with the enroll form), the
  same name sends nothing. `rename-device`'s answer replaces the cached detail; a 409 `name_taken` or a 422 `invalid`
  sits on the field, anything else beside the button. The list (the overview's counts read it) is marked stale after any
  answer, and the detail too after a failure (a rename whose answer was lost may still have landed).
- **Delete** (the danger zone, the Overview tab's last section): a confirmation that runs only with the device's name
  typed exactly, then `delete-device` (a 404 counts as deleted; any other refusal is worded in the dialog, the list
  marked stale). The page first stops showing the device, so the commit that drops it unsubscribes every query that
  reads it; then each query whose key names the device (a path parameter: detail, settings, media, conversations,
  metrics, processes; or a filter: its logs, memories, tasks, Home Assistant use; `readsDevice`) is cancelled and
  removed, the device is taken out of the cached list (marked stale), and the page goes to `/devices` with the
  focus on the content and a toast. No request reaches the deleted id afterwards, whatever the feed or a timer says.
  A delete elsewhere (another tab, an API caller) reaches the page as `device_deleted` and leaves it the same way, the
  toast saying "<name> was deleted elsewhere"; one that arrives while the page's own delete is on its way is worded as
  its own, and whichever of the answer and the event comes first leaves, once.
- **Conversations** (the device page's third tab; never prefetched, and the panel mounts only while it shows):
  `list-device-turns` 20 a page, newest first, Load older with the `next` cursor (the focus to the first older row);
  each row is the time with its seconds, the trigger (Wake word, Button, Follow-up, Event, or Not recorded), the mode,
  the user's words (an event turn's marked as the server's own) and the reply cut to 120 characters, the tools by name
  with their error codes, the tokens. Open shows `get-device-turn`'s messages as stored in a drawer: speech as text,
  tool calls and results preformatted, never markup, a result's error code (as the list reads it) in its caption. Both
  live only in the query cache, removed 30 s after nothing shows them (`TRANSCRIPT_GC_MS`): never in storage, the
  address, a log or the ssr page. The list is read again when
  the device's `turn_end` arrives.
- **Health** (the second tab; never prefetched, mounted only while it shows): `list-device-metrics` once per chart
  (CPU: `system.cpu.utilization`, the series without attributes being the total; memory used and limit; each
  mountpoint's free and limit; temperature), so one busy series cannot crowd another chart out of the server's
  50,000-point read. The Window select (15 min, 1 h by default, 6 h, 24 h, the retention) is in each key, and each read
  asks from that long before it; a window is read again about as often as a chart's point spans (10 s, 30 s, 2 min,
  5 min), and another window keeps the old charts, faded, until its points land. Storage draws, under each mount's
  meter, its used share (1 - free / limit, the limit of that round or the one before) over the window; every chart
  draws about 240 points at most (gaps found in the raw points, then runs averaged). `get-device-processes` every 30 s as
  two tables (pid, comm, cpu, rss; the server has no command line). A device without the `system.metrics` capability
  shows that it sends no metrics and reads nothing.

## Logs

`/logs` (no loader: lines may carry what third-party programs wrote, so the browser reads them, never the ssr server):
`list-logs` newest first, 200 a page. Load older asks `until` a microsecond after the oldest line shown (the store keeps
microseconds and orders by time alone), leaving out the lines at that time a page already showed, so a run of lines
sharing one time is neither lost nor shown twice (`lib/log-paging.ts`); the page holds at most 2,000 lines, then asks
for Until. Filters: speaker, source (exact), lowest level, text (`q`), From and Until in the household's zone
(`lib/zoned-time.ts`), read 300 ms after the last change; one the server would refuse (until not after since, a source
past 64 bytes, a text past 256) is said on its field and asks nothing, and a 422 `invalid` lands on the field its path
names. Read the newest reads the newest page alone again, older pages dropped first (an infinite query's refetch would
read every loaded page in turn), and so does turning Live off; no refetch on focus (a day's search can take the server
seconds). While another filter's read runs, the old lines fade and the box is `aria-busy`. Lines stay in
the query cache 30 s after nothing shows them (`LOGS_GC_MS`), never in storage or the address.

Live mounts the tail: it wants the `logs` topic while mounted (the toggle and the page's unmount let it go), shows the
lines the feed's buffer got since it opened that match the filter (the feed's device filter would scope every topic of
the tab, so the tail filters in the page), oldest first, following the end. Scrolling up pauses it: the view holds the
buffer it had (at most 2,000 lines) and counts what came since; scrolling back to the end, or Jump to the latest lines,
takes it up again. From and Until do not apply to it.

## Traces

`/traces` (no loader for the traces: the browser reads them and keeps them current) subscribes to `traces` while it
shows. The store's figures (`get-trace-stats`) are read every 2 s, as no event carries them. The list reads the newest
100 traces (`list-traces`, `device` from the address, so a device's page links to its own), then folds each span event
in place (`lib/traces/book.ts`: a span seen to start after the summary counts, a newer summary settles the rest), and
reads the traces changed since its last read (`since`, 200 a page, at most 5 pages) half a second after a span starts
or ends (at most once a second), after a `span_dropped` and after every gap of the feed. Running only, Errors only and
the name are filtered in the page. Streams are the live spans with byte counters, from the feed's `span_update`s (a
stream that started before the page opened joins at its next update); a speed falls to zero 3 s after its last update.

`/traces/$traceId` reads the trace (`get-trace`) and folds the feed's spans of it in (`withFeedSpans`), reading it again
after a gap or a `span_dropped`; a 404 says the server no longer keeps it. The waterfall nests spans under their
parents from the roots (computed again as spans arrive, so a device's batch adopts the server's spans), colours bars by
service (server `chart-1`, device `chart-2`, a failed span `destructive` with its square), grows a running span to now
and marks span events as ticks, named on the selected span; the side panel holds the span's facts, attributes, stream,
events from its start and linked traces.

## Providers, modes, settings and tokens

None of them has a live topic: each create, delete or put refreshes its own query, a create after any answer (one whose
answer was lost may still have been made). Creates and deletes are SDK calls, not TanStack mutations, so no request (a
create carries secrets) and no answer (a token) reaches the mutation cache.

- **Providers** (`/providers`): the instances by kind (in the page's order: speech, voice, model, weather, search,
  embeddings, Hermes, Home Assistant, MCP, telemetry export; a kind newer than the page after them, under its own name),
  then by name, with their module, when they were made, and each secret Set or Not set (never a value). Kinds and
  secrets come from the server's module catalog (`list-provider-modules`, read with the list, kept for the page's life:
  it changes only with the server's build), so the list shows once both are read; a module the catalog does not list (no
  longer registered, or a dev fake on a server without `CADENCE_DEV_FAKES`) lists as Unknown. Add a provider (held,
  `aria-disabled`, until the catalog is read, as its modules come from it) opens a
  dialog: a name (the server's instance name pattern, and not `modules`, the catalog's path, in any case), a module from
  the catalog grouped by kind, its config through the form renderer from the module's `configSchema` (its fields in the
  module's order)
  (`forms/schema-fields.tsx` inside the dialog's form; "This module takes no configuration." for an empty one) and one
  write-only field per secret the catalog names (required ones marked; an empty optional one is not sent). The config
  and the secret fields are keyed by the module, so nothing typed for one goes to another. The secret fields are
  uncontrolled (the secret field of a device's page, `forms/secret-input.tsx`), read only to build the request and
  cleared at once, sent or refused. The server's 422 `config_invalid` lands on the field its `path` names: `/name`,
  `/secrets/<name>`, `/secrets`, else the config's own field the pointer leads into (relative to the config), else the
  configuration as a whole; 409 `name_taken` on the name, 422 `unknown_module` on the module. Delete asks first; the
  server refuses while a setting names the instance, and the dialog words its 409 `in_use` by the code alone (the
  server names no setting), staying open.
- **Test** (each row, `test-provider`): the server builds the instance afresh and runs its module's cheapest free call.
  The row's Test column shows the outcome as a badge, in a polite live region: OK with its milliseconds, else the code's
  words from the page's table with the code itself in mono (`auth` Credential refused, `unreachable`, `timeout` Timed
  out, `bad_response` Unexpected answer, `unsupported` Cannot be tested, `rate_limited` Upstream rate limited,
  `build_failed` Does not build); a test that never ran says Not tested with its status and code (or "no answer").
  Never upstream text. One test at a time per instance: while it runs the button is `aria-disabled` and ignores
  presses (the focus stays on it). The server allows one test per instance per 5 s: its 429 shows "Wait N s", counted
  down from `Retry-After` (5 s without one), and holds the button that long. Outcomes live in the page's state only.
- **Modes** (`/modes`, after Providers in the nav): each agent mode's name, model (or Device default), reasoning,
  steps, seconds, interim text (Spoken or Dropped), tools (All for `null`, a count, or None for `[]`) and its voice
  aliases per language, by name; links to the `mode` and `allowedModes` settings, whose rows on the settings pages
  link back ("Manage the modes"). Add a mode (held, `aria-disabled`, until the list is read, whose names a create is
  checked against) and each row's Edit open one dialog for every field of the mode: a name on
  create only (the server's pattern; a name the list holds is refused, since a put under it would replace that mode),
  the model (at most 200 bytes), reasoning, steps (1–50), seconds (5–600) and interim text; an "All tools" switch
  (`tools: null`) and, off, a list of tool names (`[]` when empty; the list is kept while the switch is on); and the
  English and Russian aliases (up to 10 each, trimmed, 1–40 characters, distinct in any case). Lists add an item with
  Enter or Add (`forms/tag-list-field.tsx`), refuse one the server would with its reason, and hold the submit while
  text is typed but not added. The put sends the whole mode (`put-mode`, create or replace): 409 `alias_taken` lands
  on the alias it names («quick» is another mode's name or alias) or on the new name, 422 `invalid` on the field its
  path names (`/path/name`, `/body/<field>`, a tool or an alias by its index), anything else beside the form. Delete
  asks first; 409 `in_use` (a setting names it, the defaults `fast` and `smart` included) is worded in the dialog,
  which stays open. A create gives the focus back to Add a mode, an edit to its row's Edit button.
- **Groups** (`/groups`, after Devices in the nav): each multiroom group's name (a link to its page), kind (Group or
  Stereo pair), member count, elected leader and state (Active while the leader streams, Idle, No leader while none
  can lead). A group's page (`/groups/$id`) shows its leader, preferred leader, latency, stream and start wait, and
  each member's channel, trim, link and the sync it last reported (`media.group`: state, synced, clock error in µs,
  queue, rejoins; the leader's view of a member stands in while the member reported none), kept current by the
  `groups` topic. Add a group (held until the groups and devices are read) and Edit open one dialog: the name (1–64
  characters, no other group's in any case), the kind, then for a group 2–8 enrolled devices, each with its channel
  and trim (−500–500 ms), or for a stereo pair a left and a right speaker (a note when their boards differ); a device
  in another group is shown with it and cannot be picked. Latency (200–5000 ms: lower reacts sooner to a pause or a
  skip, higher rides out weak Wi-Fi), the preferred leader, bitrate, start wait and PCM follow. A save sends the
  whole group (`create-group`, `update-group`): 409 `name_taken` lands on the name, 409 `in_group` and 422
  `unknown_device` on the devices (a pair's side), naming the device, 422 `invalid` on the field its path names; 409
  `stereo_pair` and 404 beside the form. Delete asks first, then returns to the list. A device's page names its group
  beside its room, linked to the group's page.
- **Settings** (`/settings`): every key the global scope sets (all but `haArea`), by group (Voice, Assistant, Memory,
  Tasks and home, Telemetry: `logRetentionDays` and `telemetryExport`, each saying what the server does while unset, 7
  days and off, and the export linking to the providers page where its `otlp-http` instance is made), with its value or
  Server default,
  through the device page's settings editor in the global scope (`components/settings/`, `SettingsEditor scope`): Set
  or Edit, and Reset (`null`) back to the server's default. The global put replaces the whole set (the server's
  `PutGlobal`; a device's put is a patch), so the editor reads the set again and sends it whole with the one change
  (`lib/settings.ts`); a tab's global puts run one at a time, each reading the set only once the one before it landed,
  so two saves never undo each other. A global save also marks stale what other pages show of the set: the MCP servers
  and their tools, Hermes's kind and Home Assistant's status (no topic says when a setting changed them). The server's 422 is the authority: a `path` lands on its field, else the code shows beside the
  form (today it answers `settings_invalid` without one).
- **API tokens** (`/tokens`): name, scopes, made and last used (to the minute, or Never), by name. Create a token takes
  a name (the server's lowercase pattern) and at least one scope (`admin` checked first, `ha`, `metrics`, each with what
  it may call). The new token is shown once in the dialog, with a copy button and the note that it will not be shown
  again; it lives in the dialog's state only and goes the moment the dialog starts closing. While it shows, only Done
  closes the dialog (no scrim click, no Escape, no corner button). Revoke asks first.
- Focus: a create dialog opens on its name and gives the focus back to the page's own action (Add a provider, Add a
  mode, Create a token), since the empty state's button that may have opened it goes once the first item lands; the token box focuses
  its copy button. A delete's confirmation sends it there too once the row is gone, and back to the row's button when
  cancelled.

## Memory, tasks and integrations

Memory texts, task titles, questions, replies, results and notices, Home Assistant names and states and MCP tool
descriptions are shown on these pages only, as React text (never markup), kept in the query cache alone and never
logged. Every action is an SDK call, not a TanStack mutation, so nothing typed reaches the mutation cache; each refreshes
what it may have changed after any answer.

- **Memory** (`/memory`, follows `agent`): three sections.
  - Suggestions: the pending memories (`status=pending`, the server's most of 200), each worded New, Update or Delete
    (a proposal names the active memory it replaces). An update shows the active text it would overwrite ("Replaces:
    …"; the scopes the proposals touch are read whole, since no route reads one memory by id). Approve, Reject, and for
    a new one Edit (its text, kind and scope, patched first, then approved); a proposal is taken as made, since the
